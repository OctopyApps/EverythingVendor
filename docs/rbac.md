# RBAC — модель прав доступа

## Гранулярность прав

Права выражаются тройкой **модуль → сущность → действие**:

```
core.user:read
crm.deal:write
archive.document:delete
```

Формат ключа: `PermissionKey{Module, Entity, Action}.String()` →
`"{module}.{entity}:{action}"` (см. `internal/rbac/models.go`).

## Уровни проверки

1. **Ролевой уровень** — есть ли у пользователя роль, у которой есть данное
   право (`permissions` → `role_permissions` → `roles` → `user_roles`).
2. **Уровень записи** (`resource_grants`) — точечное разрешение/запрет на
   конкретный `record_id`, переопределяющее ролевой доступ.

## Порядок вычисления решения (`Authorizer.evaluate`)

```
1. Есть resource_grants(effect=deny) на эту запись?   → DENY  (наивысший приоритет)
2. Есть resource_grants(effect=allow) на эту запись?   → ALLOW (даже если роль не даёт доступа)
3. Есть у пользователя роль с нужным правом?            → ALLOW
4. Иначе                                                → DENY (default deny)
```

Explicit deny **всегда** побеждает allow — это осознанное решение для
случаев вида "у сотрудника есть роль с широким доступом, но конкретную
запись нужно временно закрыть вручную (например, конфликт интересов,
расследование, увольнение в процессе)".

## Таблицы БД

| Таблица | Назначение |
|---|---|
| `tenants` | мультитенантность, даже если сейчас используется один тенант |
| `users` | пользователи, `password_hash` NULL допустим для будущих внешних IdP |
| `roles` | роли тенанта; `is_system=true` — нельзя удалить/переименовать через API |
| `permissions` | глобальный справочник прав (`module`, `entity`, `action`), общий для всех тенантов |
| `role_permissions` | связка роль ↔ право |
| `user_roles` | связка пользователь ↔ роль, с `granted_by` для аудита "кто выдал" |
| `resource_grants` | точечные allow/deny на конкретную запись |
| `audit_log` | лог всех проверок доступа (allowed и denied) |

## Кэширование

Ролевые права кэшируются в Redis (`rbac:perms:{tenant_id}:{user_id}`),
TTL задаётся `RBAC_CACHE_TTL_SECONDS` (по умолчанию 60 секунд).

- **Точечные `resource_grants` НЕ кэшируются** — слишком динамичны, всегда
  проверяются напрямую в БД при наличии `record_id` в запросе.
- TTL — это только страховка. Основной механизм актуальности — явный вызов
  `Authorizer.InvalidateUserCache(ctx, tenantID, userID)` сразу после любого
  изменения ролей пользователя (см. `coreapi.Handlers.AssignRole/RevokeRole`).
- Если добавляешь новый способ менять роли пользователя (например, bulk-импорт,
  синхронизация с внешним IdP) — не забудь вызвать инвалидацию для каждого
  затронутого пользователя.

## Fail closed

`Authorizer.Check` возвращает `(Decision, error)`. Если `error != nil`
(например, недоступна БД или Redis) — **вызывающий код обязан трактовать
это как отказ в доступе**, а не пропускать запрос. Middleware
`RequirePermission` уже реализует это правильно:

```go
if err != nil || !decision.Allowed {
    writeError(w, http.StatusForbidden, "access_denied")
    return
}
```

Не убирать проверку `err != nil` при рефакторинге этого места.

## Аудит

Каждый вызов `Authorizer.Check` пишет запись в `audit_log`, независимо от
результата:

```go
Metadata: map[string]any{"action": req.Action, "reason": decision.Reason}
```

`reason` — одно из: `resource_grant_deny`, `resource_grant_allow`,
`role_permission`, `default_deny`, `evaluation_error`. Это диагностический
маркер для расследований ("почему пользователю не хватило прав именно в
этот момент") — не убирать и не упрощать при рефакторинге.

## Защита от IDOR при управлении ролями

`Repository.AssignRole` явно проверяет, что и `user_id`, и `role_id`
принадлежат заявленному `tenant_id`, прямо в SQL (`JOIN`/`WHERE` с
`tenant_id`), а не полагается на проверку до вызова. Это защищает от
попытки назначить пользователю роль из чужого тенанта, даже если
`role_id` был каким-то образом узнан/подобран.

При добавлении новых мутирующих эндпоинтов (например, будущий
"создать пользователя", "изменить email") — сохранять этот паттерн:
tenant-scoping внутри самого запроса к БД, а не только на уровне вызывающего кода.

## Известные ограничения текущей реализации

- Нет UI/API для создания кастомных ролей и назначения им прав (`permissions`) —
  сейчас это делается только через SQL/миграции. Роли `admin`/`member` — сидовые.
- Нет пагинации/фильтрации для `resource_grants` (эндпоинтов для управления
  ими вообще пока нет — только сама модель в БД и логика проверки).
- Нет unit-тестов на `Authorizer.evaluate` — это стоит сделать одним из первых
  шагов, учитывая критичность компонента (таблица истинности для всех 4 веток
  из раздела "Порядок вычисления решения").
