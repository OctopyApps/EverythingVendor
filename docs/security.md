# Security — решения и обоснование

Этот документ фиксирует **зачем** сделано именно так, чтобы при доработке
не откатить осознанные решения по незнанию контекста.

## Пароли

- **Argon2id**, параметры по OWASP Password Storage Cheat Sheet:
  `m=19456 KiB (19 MiB), t=2, p=1` (см. `internal/security/password.go`).
- Хэш хранится в самоописываемом формате
  `$argon2id$v=19$m=19456,t=2,p=1$<salt>$<hash>` — параметры зашиты в сам
  хэш, что позволяет в будущем менять их (например, повышать `m`/`t`) без
  инвалидации уже существующих хэшей — старые проверяются по своим
  сохранённым параметрам.
- Сравнение хэшей — `subtle.ConstantTimeCompare`, не `==` и не `bytes.Equal`
  (защита от timing-атаки на сравнение).
- Минимальная длина пароля — 12 символов (`authsvc.minPasswordLength`).
  Осознанно не требуем "спецсимволы/цифры/заглавные" — современные
  рекомендации (OWASP, NIST 800-63B) считают это менее эффективным, чем
  просто требование длины.

## User enumeration

`Service.Login` не различает "пользователь не найден" и "неверный пароль":
- одинаковый HTTP-статус и текст ошибки (`401 invalid_credentials`);
- при отсутствии пользователя всё равно вызывается `VerifyPassword` против
  фиктивного (`dummyHash`) хэша — чтобы время ответа не отличалось и не
  давало атакующему тайминг-канал для определения существования email.

При добавлении новых auth-related эндпоинтов (сброс пароля, приглашения
и т.д.) — сохранять этот принцип: ответ не должен позволять отличить
"такого пользователя нет" от других причин отказа.

## JWT

- **RS256**, не HS256. Причина: RS256 разделяет приватный (подпись) и
  публичный (проверка) ключи — так же устроена схема большинства OIDC-
  провайдеров (JWKS endpoint). Когда будет подключаться внешний IdP
  (см. `architecture.md`, вопрос авторизации отложен на будущее), потребуется
  просто добавить ещё один источник публичных ключей, а не менять схему
  токенов целиком.
- Алгоритм **жёстко зафиксирован** при валидации:
  `jwt.WithValidMethods([]string{jwt.SigningMethodRS256.Name})`
  (см. `internal/security/jwt.go`). Это защита от классической атаки
  "alg confusion" — когда токен с `alg: none` или `alg: HS256` (с публичным
  RSA-ключом в качестве HMAC-секрета) принимается как валидный. **Не убирать
  этот параметр** при рефакторинге `ValidateAccessToken`.
- Access-токен **не содержит списка прав пользователя**. Права проверяются
  заново на каждый запрос через `Authorizer` (БД + кэш), а не читаются из
  токена. Это значит, что отзыв роли действует практически мгновенно (в
  пределах TTL кэша, по умолчанию 60 секунд), а не только после истечения
  срока действия токена (15 минут по умолчанию). Если возникнет соблазн
  "закэшировать права в токене для производительности" — это осознанный
  компромисс security/performance, менять только по явному решению, не
  как побочный эффект оптимизации.

## Refresh-токены

- Хранятся в БД (`refresh_tokens.token_hash`) как **SHA-256**, не как
  plaintext и не как argon2id. Обоснование: refresh-токен генерируется как
  32 случайных байта (`crypto/rand`) — угроза здесь не подбор (энтропии
  достаточно), а компрометация БД, от которой достаточно быстрого
  криптографического хэша. Медленный argon2id тут не нужен и не даёт
  дополнительной защиты, только лишний CPU.
- **Ротация при каждом использовании**: `Service.Refresh` отзывает
  использованный токен (`revoked_at = now()`) и выдаёт новую пару. Это
  ограничивает окно использования украденного refresh-токена — если
  легитимный клиент и атакующий оба попытаются использовать один и тот же
  токен, второй получит `401 invalid_refresh_token`.
- Отзыв поддерживается на уровне отдельного токена (`Logout`) — полноценный
  "разлогинить со всех устройств" (отзыв всех токенов пользователя) пока не
  реализован, это кандидат на будущую доработку.

## HTTP-уровень

- `http.TimeoutHandler` на весь роутер (15 секунд) — защита от медленных/
  зависших обработчиков.
- `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout`, `IdleTimeout` заданы
  явно на `http.Server` (см. `cmd/core/main.go`) — не полагаться на дефолты
  стандартной библиотеки (там таймауты отсутствуют по умолчанию).
- Лимит размера тела запроса — 1 MiB (`http.MaxBytesReader`) на всех
  JSON-эндпоинтах, принимающих body — защита от DoS через огромный payload.
- `json.Decoder.DisallowUnknownFields()` — строгая валидация входного JSON,
  лишние поля в теле запроса приводят к ошибке, а не игнорируются молча.
- Заголовки безопасности на каждый ответ: `X-Content-Type-Options: nosniff`,
  `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`,
  `Cache-Control: no-store` (последнее особенно важно, т.к. ответы содержат
  токены и данные пользователей — не должны оседать в кэше браузера/прокси).

## SQL

- **Только параметризованные запросы** через `pgx` (`$1, $2, ...`).
  Конкатенация пользовательского ввода в SQL-строку запрещена без исключений
  во всём проекте — это правило из security-профиля проекта (см. системный
  промпт ревьюера) и применяется в том числе к Go-коду ядра, не только к
  гипотетическому Python/JS.
- `tenant_id` фильтруется в самом SQL-запросе, а не проверяется отдельно
  после получения данных — см. `coreapi.Repository.AssignRole` как пример
  паттерна (JOIN с условием на `tenant_id` прямо в INSERT/UPDATE/DELETE).

## RBAC / авторизация

Подробно — `docs/rbac.md`. Ключевой принцип уровня всего сервиса:
**fail closed**. Любая техническая ошибка при проверке доступа (недоступна
БД, недоступен Redis, ошибка десериализации) трактуется как отказ, никогда
как пропуск запроса. Это реализовано в `RequirePermission` middleware:

```go
decision, err := authorizer.Check(...)
if err != nil || !decision.Allowed {
    writeError(w, http.StatusForbidden, "access_denied")
    return
}
```

## Мультитенантность как security-граница

`tenant_id` — не просто поле для будущего SaaS, это уже сейчас граница
изоляции данных. Любой новый SQL-запрос к сущностям, привязанным к
пользователю/тенанту, обязан фильтроваться по `tenant_id`, полученному из
JWT-claims текущего пользователя (`claims.TenantID`), а не из параметров
запроса (клиент не должен иметь возможность передать произвольный
`tenant_id` и получить чужие данные).

## Что НЕ реализовано и является известным риском для продакшена

- **Rate limiting** на `/auth/login` и `/auth/register` — сейчас ничего не
  мешает перебору паролей брутфорсом. Следующий пункт в очереди работ.
- **Отзыв всех refresh-токенов пользователя разом** (например, при смене
  пароля или подозрении на компрометацию) — сейчас можно отозвать только
  по одному токену через `/auth/logout`.
- Нет **CORS-конфигурации** — если фронтенд будет на другом origin,
  понадобится явная настройка (allowlist origin, не `*`).
- Нет **CSP** (Content-Security-Policy) заголовка — актуально станет при
  появлении фронтенда, отдающего HTML.
- Нет security-логирования подозрительной активности (много неудачных
  логинов подряд, попытки доступа к чужому тенанту и т.д.) сверх базового
  `audit_log`.
