# Единая платформа компании-вендора: концепция, архитектура и план развития

## 1. Идея и позиционирование

**Продукт:** единая внутренняя (с перспективой white-label / SaaS) платформа для компании-вендора ПО, закрывающая весь операционный цикл работы с клиентом:

- **CRM** — воронка продаж, работа с клиентами и партнёрами;
- **Цифровой архив с LLM** — база знаний, документооборот, семантический поиск и RAG-помощник;
- **Почтовый модуль** — приём/разбор входящей почты, автоклассификация обращений, автоответы, маршрутизация в CRM/поддержку;
- **Модуль выдачи дистрибутивов** — автоматическая генерация лицензий, сборок и выдача клиенту дистрибутивов ПО без участия человека.

Ключевая идея — **не набор разрозненных систем, а единое ядро (core), вокруг которого модули подключаются по единому контракту**. Это даёт:

- одну модель пользователей, ролей и прав на всю платформу;
- единый источник правды по сущностям (клиент, компания, документ, лицензия — всё связано между собой);
- возможность включать/выключать модули под конкретного клиента (если платформа станет продаваемым продуктом, а не только внутренним инструментом);
- переиспользование инфраструктуры (auth, файлы, очереди, LLM-шлюз, аудит) вместо дублирования в каждом модуле.

## 2. Бизнес-план

### 2.1 Целевая аудитория

1. **Основной сценарий** — сама компания-вендор использует платформу как внутреннюю ERP/CRM-систему.
2. **Расширенный сценарий (опционально, v2+)** — платформа продаётся другим вендорам ПО как продукт (multi-tenant SaaS): у каждого клиента свой набор модулей, свои пользователи, изоляция данных.

### 2.2 Ценность для бизнеса

| Проблема сейчас | Что даёт платформа |
|---|---|
| CRM, почта, файловый архив и выдача лицензий — разные несвязанные системы | Единая карточка клиента: письма, сделки, документы, выданные лицензии — в одном месте |
| Ручной разбор входящей почты (кто клиент, что хочет, куда направить) | Автоклассификация писем LLM: тип обращения, привязка к клиенту/сделке, авто-ответ по шаблону или эскалация человеку |
| Ручной поиск информации по документации, регламентам, перепискам | Цифровой архив с семантическим поиском и RAG-чатом по всей базе знаний компании |
| Выдача дистрибутивов и лицензий — ручной процесс (создать ключ, собрать архив, отправить письмо) | Полностью автоматический пайплайн: оплата/заявка → генерация лицензии → сборка/выбор дистрибутива → письмо клиенту |
| Разные права доступа настраиваются в каждой системе отдельно | Единая ролевая модель и матрица доступа на уровне платформы |

### 2.3 Ключевые фичи по модулям

**CRM**
- карточки контактов/компаний/сделок, кастомные поля, воронки, задачи и напоминания;
- история взаимодействий (письма, звонки, встречи) в единой ленте;
- интеграция с почтовым модулем и модулем лицензий (сделка → выдача дистрибутива);
- отчётность и дашборды по продажам.

**Цифровой архив с LLM**
- хранение документов (регламенты, договоры, техдокументация, переписка) с версионированием;
- полнотекстовый + семантический (векторный) поиск;
- автотегирование и автоклассификация документов при загрузке;
- RAG-чат «спроси у базы знаний» с указанием источников;
- права доступа на уровне папок/тегов/документов, наследуемые из ролевой модели ядра.

**Почтовый модуль**
- подключение почтовых ящиков (IMAP/SMTP, Graph API/Gmail API);
- LLM-классификация входящих писем (тип обращения, тональность, срочность, привязка к клиенту);
- автоответы по сценариям (шаблон + персонализация LLM), эскалация в CRM как задача/тикет при необходимости участия человека;
- логирование и аудит всей переписки, привязка к карточке клиента в CRM.

**Модуль выдачи дистрибутивов**
- каталог продуктов/версий/сборок;
- генерация и учёт лицензионных ключей (сроки, ограничения, привязка к клиенту);
- автоматическая сборка/выбор нужного дистрибутива и безопасная отдача (подписанные ссылки, ограниченный TTL);
- интеграция с CRM (триггер — закрытие сделки/оплата) и с почтой (автоматическое письмо с дистрибутивом и лицензией).

### 2.4 Дорожная карта (бизнес-вехи)

| Веха | Содержание | Ориентировочно |
|---|---|---|
| **MVP** | Ядро (auth, роли, entity-engine) + модуль CRM в базовом объёме | Q1 |
| **v1** | Цифровой архив без LLM (хранение, версии, права) + базовый полнотекстовый поиск | Q2 |
| **v1.1** | LLM-слой над архивом: семантический поиск, автотеги, RAG-чат | Q2–Q3 |
| **v1.2** | Почтовый модуль: подключение ящиков, разбор писем, автоответы | Q3 |
| **v2** | Модуль выдачи дистрибутивов и лицензий, полная интеграция всех модулей | Q4 |
| **v2+** | Multi-tenancy, маркетплейс модулей, публичный API, white-label | далее |

### 2.5 Монетизация (если платформа станет продуктом)

- внутренний cost-center первый год (окупается за счёт экономии на ручном труде поддержки/продаж);
- далее — подписка per-seat / per-module для внешних вендоров, использующих платформу как SaaS.

## 3. Архитектурные принципы

### 3.1 Общий подход — модульный монолит с чёткими границами, готовый к выделению в микросервисы

Рекомендация: **не начинать с «микросервисов ради микросервисов»**. Начать с модульного монолита (или небольшого числа сервисов: `core`, `llm-gateway`, `worker`), где каждый модуль — отдельный пакет/сервис с чётким контрактом и собственной схемой данных в общей БД (или отдельной БД — на усмотрение). Когда конкретный модуль упрётся в нагрузку или потребует независимого масштабирования (например, обработка почты или LLM-инференс) — выделяем его в отдельный сервис. Контракт между ядром и модулями с самого начала проектируется как между независимыми сервисами (через API/события), чтобы выделение в будущем было малой кровью.

### 3.2 Ядро (Core)

Ядро не знает ничего о бизнес-логике CRM/архива/почты. Оно предоставляет:

1. **Entity Engine** — метаданные-ориентированный CRUD-движок:
   - модуль регистрирует схему сущности (поля, типы, связи, кастомные поля) через манифест;
   - ядро реализует generic CRUD, валидацию, версионирование, аудит, поиск по метаданным для любой зарегистрированной сущности;
   - технически — PostgreSQL с гибридной схемой: строгие колонки для системных полей (id, owner, created_at, tenant_id) + `JSONB` для кастомных/модульных полей, с возможностью выноса горячих полей в отдельные колонки при росте нагрузки.

2. **RBAC / модель доступа**
   - роли, разрешения на уровне: модуль → тип сущности → конкретная запись → поле;
   - поддержка групп пользователей, наследования ролей;
   - политики можно проверять как через middleware в Go-ядре, так и декларативно (например, через встроенный движок правил наподобие OPA/Cedar, чтобы не хардкодить логику доступа в каждом модуле).

3. **Реестр модулей / Module SDK**
   - модуль = манифест (какие сущности, какие права, какие меню/пункты UI, какие события публикует/слушает) + реализация (сервис на Go или Python);
   - ядро на старте/при регистрации модуля валидирует манифест и подключает модуль (миграции схемы, регистрация в API-gateway, регистрация событий).

4. **Event Bus / шина событий**
   - модули общаются между собой асинхронно через события (`crm.deal.won`, `email.received`, `archive.document.uploaded`), а не прямыми вызовами API друг друга;
   - это критично для связки CRM → выдача дистрибутивов, почта → CRM и т.д. без жёсткой связанности;
   - брокер: NATS (простота, лёгкий вес) или Kafka (если ожидается большой объём и нужен replay/долгое хранение событий). Для старта разумно взять **NATS JetStream** — проще в эксплуатации, достаточно возможностей.

5. **Сквозные сервисы**: аутентификация (OIDC/SSO), файловое хранилище (S3-совместимое, MinIO), уведомления, аудит-лог, фоновые задачи (очереди), единый API-gateway.

### 3.3 LLM-слой как отдельный сквозной сервис

LLM-функциональность нужна и архиву, и почте, и потенциально CRM (саммари сделок и т.д.) — поэтому это **не часть модуля «Архив»**, а отдельный сервис `llm-gateway`:

- единая точка входа ко всем LLM-провайдерам (Anthropic API, локальные модели и т.д.) с ретраями, лимитами, логированием стоимости;
- переиспользуемые пайплайны: классификация текста, эмбеддинги, суммаризация, RAG;
- векторное хранилище — `pgvector` (если хочется минимизировать зоопарк технологий и остаться на Postgres) либо Qdrant (если нужен отдельный высокопроизводительный векторный поиск);
- модули (архив, почта) обращаются к `llm-gateway` через внутренний API/события, а не встраивают вызовы к LLM напрямую.

### 3.4 Мультитенантность

Даже если сейчас платформа только для внутреннего использования — заложить `tenant_id` во все таблицы и в модель доступа с первого дня. Это на порядок дешевле, чем добавлять мультитенантность потом, и открывает путь к продаже платформы как SaaS в будущем.

## 4. Технологический стек и обоснование

| Компонент | Технология | Почему |
|---|---|---|
| Core API / Auth / API Gateway | **Go** | производительность, конкурентность, надёжность для системного слоя, много готовых библиотек для RBAC/gRPC/HTTP |
| Entity Engine | **Go** | горячий путь всех модулей — CRUD должен быть максимально быстрым и предсказуемым |
| Модуль CRM | **Go** (бизнес-логика) поверх Entity Engine | стандартные CRUD-сценарии, не требует ML — приоритет производительности и простоты поддержки |
| Модуль «Цифровой архив» (хранение, версии, права) | **Go** | файловые операции, метаданные — производительность |
| LLM-пайплайны (классификация, эмбеддинги, RAG) | **Python** | экосистема ML/NLP (LangChain/LlamaIndex, transformers, официальные SDK LLM-провайдеров) — здесь Python вне конкуренции |
| Почтовый модуль (парсинг, интеграция с IMAP/Graph API + LLM-классификация) | **Python** | тесно завязан на LLM-пайплайны и NLP-обработку текста |
| Модуль выдачи дистрибутивов (генерация ключей, раздача файлов) | **Go** | нагрузка на конкурентную раздачу файлов, криптография для лицензий, важна надёжность |
| Асинхронные фоновые задачи (Python-сторона) | **Celery / arq** | стандарт для Python-воркеров |
| Асинхронные задачи (Go-сторона) | **River / asynq** поверх очередей | нативная интеграция с Go-сервисами |
| Шина событий | **NATS JetStream** (или Kafka при росте объёма) | лёгкая эксплуатация, паб/саб + очереди + persistence в одном |
| Основная БД | **PostgreSQL** | зрелость, JSONB для гибких схем, pgvector для эмбеддингов, надёжность |
| Векторный поиск | **pgvector** (старт) → Qdrant/Milvus (при росте) | не плодить лишнюю инфраструктуру на старте |
| Полнотекстовый поиск | **OpenSearch/Elasticsearch** (если объёмы архива большие) или встроенный `tsvector` Postgres на старте | стартовать проще, мигрировать при росте объёма документов |
| Файловое хранилище | **S3-совместимое (MinIO on-prem или облачный S3)** | стандарт де-факто для бинарных файлов/дистрибутивов |
| Кэш/очереди-брокер для Celery | **Redis** | стандарт, низкий порог входа |
| Права доступа (policy engine) | **OPA (Open Policy Agent)** или собственный движок на Go | декларативные политики вместо хардкода в каждом модуле |
| Frontend | **SPA (React или Vue) + TypeScript**, браузер | требование пользователя — только браузерный фронт; модули платформы = отдельные разделы/микрофронтенды в общей оболочке |
| API между front и back | **REST/JSON** снаружи, **gRPC** между внутренними сервисами | простота для фронта, эффективность и строгие контракты внутри системы |
| Контейнеризация/деплой | **Docker + Kubernetes (или Docker Compose на старте)** | путь к масштабированию без переписывания архитектуры |
| Observability | **OpenTelemetry + Prometheus/Grafana + Loki** | единый стандарт трассировки/метрик/логов на весь модульный ландшафт |
| CI/CD | **GitHub Actions / GitLab CI** | стандартный выбор, гибко под модульную структуру (свои пайплайны на модуль) |

## 5. Контракт «Ядро ↔ Модуль»

Чтобы модули были действительно независимыми и подключаемыми, у каждого модуля должен быть манифест примерно такого вида (концептуально, не итоговая схема):

```yaml
module: crm
version: 1.0.0
entities:
  - name: deal
    fields: [title, amount, stage, owner_id, contact_id]
    permissions: [read, write, delete, export]
  - name: contact
    fields: [name, email, phone, company_id]
events:
  publishes: [crm.deal.created, crm.deal.won, crm.deal.lost]
  subscribes: [email.classified, archive.document.linked]
ui:
  menu_items: [Сделки, Контакты, Компании]
api:
  base_path: /api/crm
```

Ядро на основе манифеста:
- создаёт/мигрирует нужные таблицы (или JSONB-схемы) в Entity Engine;
- регистрирует права по умолчанию в RBAC;
- подключает модуль к API-gateway по `base_path`;
- подписывает модуль на нужные топики в шине событий.

Это даёт возможность в будущем не просто «включать/выключать» модуль конфигом, а буквально разворачивать/останавливать его как отдельный сервис без изменения ядра.

## 6. План для разработчиков

### Фаза 0. Фундамент (инфраструктура и ядро)
1. Поднять базовый скелет: репозиторий(и), CI, Docker Compose для локальной разработки (Postgres, Redis, NATS, MinIO).
2. Реализовать в Go: сервис аутентификации (OIDC-совместимый), базовую модель пользователей/ролей/прав (RBAC).
3. Реализовать Entity Engine (Go): генерик CRUD на основе манифестов сущностей, миграции схем, базовый REST API поверх него.
4. Реализовать реестр модулей: механизм регистрации манифеста, простейший API-gateway (роутинг по `base_path`).
5. Поднять шину событий (NATS JetStream) и обвязку (publish/subscribe helper-библиотеки для Go и Python).
6. Каркас фронтенда: оболочка (shell) с аутентификацией, динамическим меню на основе подключённых модулей.

*Критерий готовности фазы:* можно зарегистрировать «пустой» тестовый модуль, увидеть его сущность в UI, выполнить CRUD с проверкой прав.

### Фаза 1. Модуль CRM (Go)
1. Сущности: контакт, компания, сделка, задача, взаимодействие (лог).
2. Воронки/стадии сделок, базовые отчёты.
3. UI: списки, карточки, канбан-доска сделок.
4. Публикация событий (`crm.deal.won` и т.д.) для будущей интеграции с модулем лицензий.

*Это первый модуль ради двух целей:* закрыть базовую бизнес-потребность и обкатать сам контракт «ядро ↔ модуль» на реальном кейсе.

### Фаза 2. Цифровой архив — базовая часть (Go)
1. Загрузка/хранение файлов (интеграция с MinIO/S3), версионирование документов.
2. Права доступа на уровне папок/тегов поверх RBAC ядра.
3. Полнотекстовый поиск (для старта — `tsvector` Postgres, не выносить в отдельный Elasticsearch, пока объём не потребует).

### Фаза 3. LLM-слой и «умный» архив (Python)
1. Поднять сервис `llm-gateway` (Python, FastAPI): единая точка вызова LLM, кэширование, лимиты, логирование стоимости.
2. Пайплайн эмбеддингов документов → `pgvector`.
3. Семантический поиск по архиву.
4. RAG-чат по базе знаний (с указанием источников/цитированием документов).
5. Автотегирование/автоклассификация документов при загрузке (подписка на событие `archive.document.uploaded`).

### Фаза 4. Почтовый модуль (Python)
1. Подключение почтовых ящиков (IMAP и/или Graph API/Gmail API), фоновый воркер на Celery/arq.
2. Классификация входящих писем через `llm-gateway` (тип обращения, привязка к клиенту/сделке — сопоставление по email/домену с сущностями CRM).
3. Автоответы: шаблоны + персонализация через LLM, с порогом уверенности — при низкой уверенности эскалация как задача в CRM.
4. Публикация события `email.classified`, на которое подписан CRM (создание/обновление сделки или задачи).

### Фаза 5. Модуль выдачи дистрибутивов (Go)
1. Каталог продуктов и версий, хранение бинарников в S3/MinIO.
2. Генерация и учёт лицензионных ключей (криптографически подписанные, с TTL/ограничениями).
3. Подписка на событие `crm.deal.won` → автоматический запуск выдачи: генерация лицензии + подготовка ссылки на дистрибутив.
4. Публикация события, на которое подписывается почтовый модуль → автоматическое письмо клиенту с лицензией и ссылкой на скачивание.
5. Аудит выдач, отзыв/перевыпуск лицензий.

### Фаза 6. Зрелость платформы
1. Мультитенантность «в полную силу»: изоляция данных между тенантами, биллинг (если продаём вовне).
2. Наблюдаемость: полноценный OpenTelemetry-трейсинг сквозь все модули и события.
3. Публичный API платформы + возможность сторонних модулей (маркетплейс).
4. Вынос отдельных модулей в независимо масштабируемые сервисы там, где это оправдано нагрузкой (в первую очередь — кандидаты: почтовый модуль и llm-gateway).

---

## 7. Риски и на что обратить внимание

- **Не переусложнять ядро.** Соблазн сделать «супер-универсальный» Entity Engine очень велик — держать в фокусе только то, что реально нужно модулям, расширять по мере необходимости, а не заранее.
- **Границы модулей через события, а не прямые вызовы.** Прямые синхронные вызовы между модулями быстро превращают систему в скрытый монолит с непрозрачными зависимостями.
- **LLM-стоимость и надёжность.** Вынос всех LLM-вызовов в `llm-gateway` с самого начала — единственный способ централизованно контролировать расходы, ретраи и деградацию при недоступности провайдера.
- **Права доступа — сквозная модель с первого дня.** Если каждый модуль начнёт изобретать свою мини-модель прав, унифицировать это позже будет очень дорого.
- **Мультитенантность закладывается заранее**, даже если пока не используется — ретрофит намного дороже.
