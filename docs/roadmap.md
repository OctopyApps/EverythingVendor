# Roadmap — план разработки

Полный бизнес-контекст и обоснование архитектуры → `docs/architecture.md`
(разделы 2 и 6). Здесь — рабочий чеклист статуса по фазам, чтобы быстро
понимать "где мы сейчас".

## Фаза 0. Фундамент (инфраструктура и ядро) — В ПРОЦЕССЕ

- [x] Docker Compose: Postgres, Redis, NATS JetStream
- [x] Auth-сервис (Go): регистрация, логин, refresh (с ротацией), logout
- [x] Модель RBAC: роли/права/точечные resource_grants, схема БД
- [x] Authorizer: default deny, explicit deny, кэш в Redis, аудит каждой проверки
- [x] Core API: CRUD-эндпоинты для users/roles (список, получение, назначение/отзыв ролей)
- [x] Rate limiting на `/auth/login` (по IP + по аккаунту) и `/auth/register` (по IP),
      с конфигурируемым fail-mode при недоступности Redis — см. `docs/security.md`
- [x] Отзыв всех refresh-токенов пользователя разом (`POST /auth/logout-all` самообслуживание,
      `POST /api/core/users/{id}/revoke-sessions` админский)
- [x] **Тех.долг закрыт**: `POST /auth/register` теперь отдаёт стабильные машиночитаемые
      коды (`invalid_email`, `weak_password`) вместо сырого текста ошибки
- [x] Управление правами роли через API: `POST /api/core/roles`, `DELETE /api/core/roles/{id}`
      (защита is_system), `GET/POST /api/core/roles/{id}/permissions`,
      `DELETE .../permissions/{permission_id}`, `GET /api/core/permissions` (каталог).
      Миграция 0003: права `core.permission:read`, `core.resource_grant:read/write`.
- [x] Управление `resource_grants` через API: `GET/POST /api/core/resource-grants`,
      `DELETE .../{id}` (upsert по effect при повторной выдаче)
- [x] `Authorizer.InvalidateRoleCache` — массовая инвалидация кэша всех носителей роли
      при изменении её прав (в дополнение к InvalidateUserCache)
- [ ] Реестр модулей / Module SDK (схема манифеста и валидация, регистрация в API-gateway,
      подписка на события) — см. architecture.md §3.2 п.2 и §5. **Следующий шаг.**
      Важно: Entity Engine в проекте не будет — каждый модуль всегда отдельный сервис со своей
      БД/схемой и обязательным `api.service_url` (без исключений для Go-модулей); реестр
      только валидирует манифест, засеивает permissions в RBAC и регистрирует роутинг, никаких
      миграций схем данных не выполняет; автоматическое скачивание/разворачивание модулей («магазин
      модулей») сознательно отложено в Фазу 6 — см. architecture.md §5.1 и причины (риск
      supply-chain атаки и обхода RBAC).
- [ ] Authorization API (`POST /api/core/authorize`) над `Authorizer.Check` — обязателен для
      любого модуля, поскольку каждый модуль — отдельный процесс и не имеет прямого доступа
      к `Authorizer` в процессе; включает выбор способа аутентификации модуля перед эндпоинтом
      (service-to-service JWT/mTLS — не решено) — см. architecture.md §3.2 п.5, §7.
- [ ] Обвязка publish/subscribe для NATS JetStream (Go + Python helper-библиотеки)
- [ ] Каркас фронтенда (shell с аутентификацией, динамическое меню)
- [ ] **UI для управления ролевыми политиками** — экран админа над core API:
      список пользователей/ролей, назначение/отзыв ролей, управление правами
      ролей и resource_grants (API уже готово). Логично делать после каркаса
      фронтенда, первым экраном после аутентификации.
- [x] Integration-тесты на auth-flow и core API (чёрно-ящичные HTTP-тесты в `ev-core/tests/`:
      register/login/refresh/logout, default deny, управление ролями)
- [x] Unit/integration-тесты на `Authorizer.evaluate` напрямую (`internal/rbac/authorizer_test.go`,
      бьют в реальный Postgres+Redis) — полная таблица истинности всех веток решения
      + инвалидация кэша по пользователю и по роли

*Критерий готовности фазы (из architecture.md):* можно зарегистрировать
тестовый модуль-сервис через его манифест, увидеть его пункт меню в UI, выполнить запрос к его
`service_url` через API-gateway с проверкой прав через `POST /api/core/authorize`. Мы ещё
не дошли до реестра модулей и до Authorization API — ядро пока работает
только со своими собственными сущностями (`users`, `roles`).

## Фаза 1. Модуль CRM (Go, отдельный сервис) — НЕ НАЧАТА

- [ ] Собственная БД/схема сервиса, собственные миграции: контакт, компания, сделка, задача, взаимодействие (лог)
- [ ] Воронки/стадии сделок, базовые отчёты
- [ ] UI: списки, карточки, канбан-доска сделок
- [ ] Проверка прав на каждый запрос через `POST /api/core/authorize` ядра (своего `Authorizer` у CRM нет)
- [ ] Публикация событий (`crm.deal_won` и т.д.) через NATS

## Фаза 2. Цифровой архив — базовая часть (Go) — НЕ НАЧАТА

- [ ] Загрузка/хранение файлов (MinIO/S3), версионирование
- [ ] Права доступа на уровне папок/тегов поверх RBAC ядра
- [ ] Полнотекстовый поиск (`tsvector` Postgres для старта)

## Фаза 3. LLM-слой и «умный» архив (Python) — НЕ НАЧАТА

- [ ] Сервис `llm-gateway` (FastAPI)
- [ ] Эмбеддинги документов → `pgvector`
- [ ] Семантический поиск, RAG-чат
- [ ] Автотегирование/автоклассификация документов

## Фаза 4. Почтовый модуль (Python) — НЕ НАЧАТА

## Фаза 5. Модуль выдачи дистрибутивов (Go) — НЕ НАЧАТА

## Фаза 6. Зрелость платформы — НЕ НАЧАТА

- [ ] Полноценная мультитенантность (сейчас только заложена в схеме БД,
      onboarding новых тенантов не реализован — `defaultTenantID` захардкожен)
- [ ] Внешний OIDC-провайдер (Keycloak/Dex/Auth0) — токены уже спроектированы
      на RS256 специально для дешёвой миграции, см. `docs/security.md`
- [ ] Магазин модулей с автоустановкой сервисных модулей: курируемый/модерируемый
      индекс модулей, проверка подписи/чек-суммы образа перед разворачиванием,
      изоляция каждого модуля (namespace/service account), явное подтверждение админом
      конкретной записи каталога перед установкой — см. architecture.md §5.1
- [ ] Оценить переход с Docker на запуск модулей как обычных процессов на голой ОС
      (systemd-юниты или аналог) — намерение на будущее, формат манифеста/`service_url`
      уже не зависит от способа запуска — см. architecture.md §7

## Как пользоваться этим файлом

При завершении пункта — отмечать `[x]` и синхронизировать со статусом в
`CLAUDE.md` (раздел "Текущий статус"), чтобы оба файла не расходились.
При начале новой фазы — можно расписать её подробнее, беря техническое
описание из `docs/architecture.md` §6 как основу.
